# 主 Markdown Viewer 的 Mermaid 与图片显示方案

## 摘要

* 复杂度评估：中高。这个任务不是单纯加一个渲染器，而是要在现有主 Markdown viewer 里同时处理“可编辑”和“可预览”两种模式，并且让 Mermaid 图和 Markdown 图片链接都能稳定显示。

* 最终目标：

  * 主 Markdown viewer 右上角增加模式开关，默认进入 `viewer`。

  * `viewer` 模式下，普通 Markdown 继续可编辑，Mermaid 图以渲染结果显示，Markdown 图片链接以图片形式显示。

  * `edit` 模式下，Mermaid 以源码可编辑形式显示，普通 Markdown 仍保持现有编辑体验。

* 范围确认：

  * 只处理主 Markdown viewer，不改聊天消息 Markdown 渲染器。

  * 只覆盖 Markdown 中已有的图片链接显示，不新增图片上传、粘贴写入或独立的图片资源管理。

  * Mermaid 渲染使用官方 `mermaid` 包，不自行实现 Mermaid 语法或布局。

## 现状判断

当前仓库里的 Markdown 相关能力已经分成两条链路：

* 主文档 viewer：`packages/ui/src/utils/markdownDocument.ts` 负责创建 Milkdown Crepe 编辑器。

* 聊天消息渲染：`packages/ui/src/components/MarkdownContent.vue` 负责轻量 Markdown 输出。

这次需求明确指向“主 markdown viewer（右上角）”，所以实现落点应当在 `packages/ui/src/utils/markdownDocument.ts` 和 `packages/ui/src/components/DocumentEditorPane.vue` 一线，而不是聊天消息渲染器。

另外，Crepe 不是完全黑盒。`@milkdown/crepe` 的 `CodeMirror` code block 组件本身就有 `renderPreview` 和 `previewOnlyByDefault` 这条预览链路，LaTeX feature 也是基于这个扩展点接入的。所以 Mermaid 不需要改 Milkdown 内核，只需要在现有 code block preview hook 上接一层自己的渲染适配。

## 方案

### 1. 在主 Markdown viewer 增加模式开关

右上角增加一个模式开关，状态取值为：

* `viewer`

* `edit`

默认值是 `viewer`。

语义如下：

* `viewer`：普通 Markdown 继续可编辑，Mermaid 代码块和图片链接以预览形式显示。

* `edit`：普通 Markdown 继续可编辑，Mermaid 代码块显示源码，图片链接继续按 Markdown 源码显示。

这里的“可编辑”不是把整个页面切成只读预览，而是保留当前 Milkdown 编辑链路，只把 Mermaid 这类内容从源码视图切换成预览视图。

### 2. Mermaid 通过 Milkdown 的 code block preview hook 接入

在 `packages/ui/src/utils/markdownDocument.ts` 里，继续使用 Crepe 的 `CodeMirror` feature，但把 `renderPreview` 配置为可识别 `mermaid` 语言。

行为定义：

* `viewer` 模式下，遇到 fenced code ` ```mermaid ` 时，`renderPreview` 返回 Mermaid 渲染结果。

* `edit` 模式下，遇到 `mermaid` 时，`renderPreview` 返回 `null`，让它保持源码编辑态。

建议新增一个独立工具函数：

```ts
export function renderMermaidPreview(
    language: string,
    content: string,
    applyPreview: (value: null | string | HTMLElement) => void
): void | null;
```

这个函数内部只做三件事：

* 懒加载并初始化 Mermaid。

* 对 `mermaid` 语言调用官方渲染 API。

* 将渲染后的 SVG 或错误占位回填到 `applyPreview`。

初始化参数建议：

* `startOnLoad: false`

* `securityLevel: 'strict'`

这样可以保证不会自动扫描整页，也能降低动态 HTML 注入风险。

### 3. 图片链接显示走 Markdown 图片语法

图片显示不引入单独的图片上传能力，只覆盖 Markdown 里的图片链接语法，例如：

```md
![diagram](https://example.com/diagram.png)
```

需要支持的展示范围：

* 远程 URL 图片

* `data:image/...` 图片

* 本地相对路径图片，例如 `![diagram](./images/diagram.png)`

不处理的范围：

* 本地文件上传

* 通过编辑器自动写回知识库的图片资源管理

实现上建议复用 Milkdown 的 image node 能力，而不是在 viewer 外层再造一层图片解析器。相对路径图片应当按当前文档所在目录解析为可访问 URL，再进入同一套图片展示链路，这样图片仍然属于 Markdown 文档的一部分，不会把主编辑链路拆成两套。

### 4. `DocumentEditorPane` 负责模式切换和状态保全

在 `packages/ui/src/components/DocumentEditorPane.vue` 里增加一个局部模式状态，并把右上角模式按钮和该状态绑定。

建议行为：

* 初始进入 `viewer`。

* 切换到 `edit` 前，先把当前 editor 的 markdown 写回 `modelValue`，避免切换丢内容。

* 切换后重建 Milkdown editor，让 `renderPreview` 依据新模式重新生效。

这样做的原因是 Crepe 的 code block preview 状态是编辑器内部状态的一部分，单纯改一个外部 flag 不一定能把已经创建好的 code block view 统一切换到新模式。重建 editor 成本可接受，而且逻辑更稳。

## 实现要点

### 1. 数据流

* `DocumentWorkspaceView.vue` 继续把 `draftContent` 传给 `DocumentEditorPane.vue`。

* `DocumentEditorPane.vue` 维护当前 viewer 模式。

* `markdownDocument.ts` 根据当前模式决定 Mermaid 是预览还是源码编辑。

* 图片链接仍按 Markdown 文本内容自然流转，不单独建立新的数据通道。

### 2. 组件职责边界

* `DocumentEditorPane.vue` 负责模式切换、editor 生命周期、保存按钮和文档头部展示。

* `markdownDocument.ts` 负责 Milkdown Crepe 的创建与 Mermaid preview hook。

* `mermaidPreview.ts` 负责 Mermaid 初始化和 SVG 生成。

* 相对路径图片解析应当复用当前文档路径作为基准目录，转换为可加载的图片地址后再交给 image node 或预览层。

### 3. 错误处理

Mermaid 渲染失败时，不让错误冒泡打断 editor。

推荐行为：

* 渲染成功：显示 SVG。

* Mermaid 语法错误：在 preview 区显示简短错误提示。

* 其他异常：回退到源码视图或空预览，避免页面崩掉。

### 4. 样式约束

需要补充主 Markdown viewer 内的图片样式和 Mermaid 预览样式：

* 图片最大宽度 100%

* 图片高度自适应

* Mermaid 图支持横向滚动，避免超宽挤爆布局

* 预览内容保持与现有深色编辑器风格一致

* 不引入新的卡片化容器，不把主编辑区做成嵌套卡片

## 验证与验收

建议按以下顺序验证：

1. `pnpm lint`
2. `pnpm --filter @packages/ui test`
3. `pnpm --filter web build`
4. `pnpm --filter web test:e2e`
5. 如果扩展端也要覆盖，再跑 `pnpm --filter extension test:e2e`
6. 扩展 E2E 通过后，执行 `pnpm --filter extension build`

验收场景：

* 打开包含普通 Markdown、Mermaid 代码块、图片链接的文档，默认进入 `viewer`。

* `viewer` 模式下 Mermaid 显示成图，远程图片、data URL 图片和本地相对路径图片都显示成实际图片。

* 点击右上角模式开关切到 `edit`，Mermaid 显示源码并可修改。

* 切换前后内容不丢失，保存按钮行为不变。

* Web 与 Extension 的主文档 viewer 行为一致。

## 风险与约束

* Mermaid 官方渲染依赖动态 DOM，必须控制初始化时机，避免在组件卸载后继续回填。

* 如果把 Mermaid 直接塞进已创建好的 editor view，状态同步会更复杂，所以建议通过重建 editor 处理模式切换。

* 本地相对路径图片需要依赖当前文档路径进行解析，文档移动、重命名或目录切换时要重新计算图片地址。

* 这次不纳入聊天消息 Markdown 渲染器，避免任务边界被拉大。

* 这次不纳入图片上传、拖拽图片等能力，避免引入新的 context provider 和文件管理改造。
