# 核心命名重构建议

## 背景

当前 `packages/core` 中有几组核心抽象在语义上存在重叠或命名过宽的问题：

- `IStorageProvider` 与 `IConversationStorageProvider` 的方法签名完全一致，但名字暗示了两套不同抽象
- `IHistoryProvider` 实际表达的是“外部会话来源”，而不是泛义上的“历史”
- `ProviderRuntime` 实际只负责模型 provider 的解析与实例化，但命名过于宽泛

这些问题在代码阅读、架构图表达和后续接口扩展时都会造成歧义。

本文件的目标不是直接改代码，而是先收敛命名与职责边界，为后续重构提供统一方向。

## 重构目标

本次建议只包含以下 3 项：

1. 统一 `IStorageProvider` 与 `IConversationStorageProvider` 为 `IConversationPersistProvider`
2. 将 `IHistoryProvider` 改为 `IExternalConversationProvider`
3. 将 `ProviderRuntime` 改为 `ModelProviderRuntime`

---

## 1. 统一 `IStorageProvider` 与 `IConversationStorageProvider` 为 `IConversationPersistProvider`

### 当前问题

当前：

- `IConversationStorageProvider`
- `IStorageProvider`

都提供相同的 4 个能力：

- `saveConversation`
- `getConversation`
- `getAllConversations`
- `deleteConversation`

这说明它们在现阶段没有形成真实的分层，只是命名重复。

其中：

- `IStorageProvider` 名字过大，容易让人误以为它未来会承载任意工作区存储
- `IConversationStorageProvider` 名字更准确，但“Storage”仍然偏泛

### 建议命名

统一为：

```ts
export interface IConversationPersistProvider {
  id: string;
  saveConversation(chat: Conversation): Promise<void>;
  getConversation(id: string): Promise<Conversation | null>;
  getAllConversations(): Promise<Conversation[]>;
  deleteConversation(id: string): Promise<void>;
}
```

### 命名理由

- `Conversation`：明确它只处理会话对象，不处理知识文档、配置或其他资源
- `Persist`：强调这是“持久化契约”，而不是广义存储能力总线
- `Provider`：保持与现有 provider 风格一致

### 职责边界

`IConversationPersistProvider` 只负责：

- 会话保存
- 会话读取
- 会话列表
- 会话删除

它不负责：

- 外部历史抓取
- 知识文档读写
- 同步传输
- 模型请求

### 迁移影响

需要调整的主要引用点包括：

- `packages/core/src/interfaces/IStorageProvider.ts`
- `packages/core/src/interfaces/IConversationStorageProvider.ts`
- `packages/core/src/providers/storage/*`
- `packages/ui/src/store/chat.ts`
- `apps/*/src/sync.ts`
- `apps/extension/src/persistence/saveCompareConversation.ts`

### 推荐做法

- 先新增 `IConversationPersistProvider`
- 再让现有实现类逐步改为实现新接口
- 最后删除 `IStorageProvider` 与 `IConversationStorageProvider`

---

## 2. 将 `IHistoryProvider` 改为 `IExternalConversationProvider`

### 当前问题

`IHistoryProvider` 的当前职责并不是“任意历史查询”，而是：

- 列出外部会话摘要
- 获取某个外部会话详情
- 作为“导入到本地工作台”的来源

当前接口：

```ts
export interface IHistoryProvider {
  id: ExternalHistoryProviderId;
  getHistoryList(options?: HistoryListQueryOptions): Promise<ConversationHistorySummary[]>;
  getHistoryDetail(externalId: string): Promise<Conversation>;
}
```

问题在于：

- `History` 语义太泛
- 无法清楚表达它是“外部来源”
- 容易与本地会话历史、同步历史、分析历史等概念混淆

### 建议命名

改为：

```ts
export interface IExternalConversationProvider {
  id: ExternalConversationProviderId;
  getConversationList(options?: ExternalConversationQueryOptions): Promise<ConversationSummary[]>;
  getConversationDetail(externalId: string): Promise<Conversation>;
}
```

说明：

- 如果想控制改动面，第一阶段也可以只改接口名，不立即改方法名
- 但从长期一致性看，`getHistoryList/getHistoryDetail` 也建议后续一起收敛为 `getConversationList/getConversationDetail`

### 命名理由

- `External`：明确来源是外部系统，而非本地存储
- `Conversation`：明确返回的是会话对象，不是通用历史记录
- `Provider`：保持 provider 风格一致

### 职责边界

`IExternalConversationProvider` 只负责：

- 外部会话来源枚举
- 外部会话详情读取
- 导入前预览来源提供

它不负责：

- 本地会话持久化
- 同步存储
- 模型发送

### 迁移影响

需要调整的主要引用点包括：

- `packages/core/src/interfaces/IHistoryProvider.ts`
- `packages/core/src/providers/model/ChatGPTWebProvider.ts`
- `packages/core/src/providers/history/gemini/*`
- `apps/web/src/providerRuntime.ts`
- `apps/extension/src/providerRuntime.ts`
- `apps/desktop/src/providerRuntime.ts`
- `packages/ui/src/store/chat.ts`

### 推荐做法

- 第一阶段先改接口名和类型名
- 第二阶段再评估是否同时改方法名与数据类型名
- 图和文档中应优先使用新名，避免继续固化 `HistoryProvider` 语义

---

## 3. 将 `ProviderRuntime` 改为 `ModelProviderRuntime`

### 当前问题

`ProviderRuntime` 当前职责是：

- 返回可用 provider 列表
- 返回 provider catalog
- 获取 provider 支持的模型
- 实例化某个模型 provider

也就是说，它实际只服务于模型 provider。

但 `ProviderRuntime` 这个名字过于宽泛，容易让人误以为它还统一管理：

- `IExternalConversationProvider`
- `IContextProvider`
- `IConversationPersistProvider`
- `ISyncTransport`

而当前实现并没有做到这一点。

### 建议命名

改为：

```ts
export interface ModelProviderRuntime {
  getAvailableProviders(): ProviderConfig[];
  getProviderCatalog(): ProviderConfig[];
  getProviderModels(providerId: string): Promise<ProviderModelCatalog>;
  getProvider(providerId: string, options?: { fresh?: boolean }): IModelProvider;
}
```

### 命名理由

- `ModelProvider`：明确 runtime 作用域就是模型 provider
- `Runtime`：保留“按宿主环境装配 provider”的语义

### 职责边界

`ModelProviderRuntime` 只负责：

- 模型 provider 的过滤
- 模型 provider 的创建
- 模型目录的加载

它不负责：

- 外部历史 provider 管理
- context provider 管理
- conversation persist provider 管理

### 迁移影响

需要调整的主要引用点包括：

- `packages/core/src/runtime/providerRuntime.types.ts`
- `packages/core/src/runtime/createProviderRuntime.ts`
- `packages/core/src/workflows/compare/*`
- `packages/core/src/agents/runtime/*`
- `apps/web/src/providerRuntime.ts`
- `apps/extension/src/providerRuntime.ts`
- `apps/desktop/src/providerRuntime.ts`
- `apps/desktop/main/providerHost.ts`
- `apps/extension/entrypoints/background.ts`

### 推荐做法

- 第一阶段先改类型名和文件内导出名
- 第二阶段再决定是否把文件名 `providerRuntime.types.ts`、`createProviderRuntime.ts` 也同步重命名为：
  - `modelProviderRuntime.types.ts`
  - `createModelProviderRuntime.ts`

## 4. 新增 `ConversationWorkflowController`

### 当前问题

当前普通对话发送链路没有独立的工作流控制类，主要编排逻辑集中在：

- `packages/ui/src/store/chat.ts`
- `useChatStore.sendDraft()`

这段逻辑当前同时承担了以下职责：

- 校验草稿输入与当前会话状态
- 在需要时创建新会话
- 生成用户消息与 assistant 占位消息
- 解析当前发送目标 provider / model
- 决定是走普通 `IModelProvider.sendMessage(...)` 还是 `AgentRuntime.run(...)`
- 处理流式更新与最终结果
- 回填 `requestSnapshot`
- 更新当前 `Conversation`
- 触发后续持久化

这说明普通对话已经存在“事实上的工作流控制器”，只是还没有被显式抽象出来，而是混在 UI store 中。

### 建议命名

新增：

```ts
export class ConversationWorkflowController {
  ...
}
```

### 命名理由

- `Conversation`：明确它负责的是普通会话发送工作流
- `Workflow`：强调它编排的是一条完整执行链路，而不是单次 provider 调用
- `Controller`：与 `CompareWorkflowController` 处于同一层级，保持概念对称

### 职责边界

`ConversationWorkflowController` 负责：

- 编排普通对话发送流程
- 创建和更新会话中的 user / assistant 消息
- 调用 `ModelProviderRuntime` 获取执行 provider
- 在 agent 模式下委托 `AgentRuntime`
- 将结果写回 `Conversation`
- 委托 `IConversationPersistProvider` 做持久化

它不负责：

- UI 组件状态
- 侧边栏切换
- 预览模式切换
- 外部历史来源管理

### 建议依赖

建议依赖关系为：

- `ConversationWorkflowController -> ModelProviderRuntime`
- `ConversationWorkflowController -> AgentRuntime`
- `ConversationWorkflowController -> IConversationPersistProvider`
- `ConversationWorkflowController -> Conversation`

### 当前实现位置

当前这一职责主要落在：

- `packages/ui/src/store/chat.ts` 的 `sendDraft()`

后续重构目标应是：

- `chatStore` 保留 UI 状态与页面交互状态
- `ConversationWorkflowController` 承担普通对话发送编排

### 迁移影响

主要影响点包括：

- `packages/ui/src/store/chat.ts`
- `packages/core/src/agents/runtime/*`
- `packages/core/src/runtime/*`
- `packages/core/src/interfaces/IModelProvider.ts`
- `packages/core/src/interfaces/IStorageProvider.ts`

### 推荐做法

- 第一阶段先在 `packages/core` 中引入 `ConversationWorkflowController`
- 第二阶段将 `sendDraft()` 中的发送编排逻辑迁移进去
- 第三阶段让 `chatStore` 退回为 UI 状态容器，只负责调用 controller


---

## 建议的实施顺序

建议按以下顺序执行，降低重构风险：

1. 先重命名 `ProviderRuntime -> ModelProviderRuntime`
   - 影响集中，语义收益高，且不会立即触及数据模型
2. 再重命名 `IHistoryProvider -> IExternalConversationProvider`
   - 先把“外部来源”语义理顺
3. 最后统一 `IStorageProvider` 与 `IConversationStorageProvider`
   - 这一步影响面最大，建议在已有命名稳定后收口
4. 在核心命名稳定后，引入 `ConversationWorkflowController`
   - 将普通对话主流程从 UI store 中抽离

---

## 建议的最小落地步骤

### 第一步：类型别名过渡

先引入新名字，并让旧名字暂时作为兼容别名存在。例如：

```ts
export interface IConversationPersistProvider { ... }
export type IStorageProvider = IConversationPersistProvider;
export type IConversationStorageProvider = IConversationPersistProvider;
```

```ts
export interface IExternalConversationProvider { ... }
export type IHistoryProvider = IExternalConversationProvider;
```

```ts
export interface ModelProviderRuntime { ... }
export type ProviderRuntime = ModelProviderRuntime;
```

### 第二步：批量替换内部引用

在内部实现与 UI/store 中优先替换为新名字，控制旧名字只作为短期兼容层存在。

### 第三步：清理旧命名

在全部引用完成迁移后：

- 删除旧接口名
- 更新导出入口
- 更新架构图
- 更新文档与 OpenSpec

---

## 结论

这 3 项重构的共同目标，是让核心抽象的名字更贴近真实职责：

- `IConversationPersistProvider`：表达“本地/同步会话持久化”
- `IExternalConversationProvider`：表达“外部会话来源”
- `ModelProviderRuntime`：表达“模型 provider 装配运行时”

在此基础上，`ConversationWorkflowController` 负责把“普通对话主流程”从 UI store 中抽离出来，与 `AgentRuntime`、`CompareWorkflowController` 一起形成更清晰的核心编排层。

再往后一步，统一的 bridge / RPC 抽象负责把这些核心接口稳定地暴露到 Desktop、Web 与 Extension 等不同宿主中。

如果后续继续推进核心层清理，建议优先保持“一个名字只表达一种职责”，避免再次出现“同签名多接口”或“过宽 runtime 命名”的情况。
