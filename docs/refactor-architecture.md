# 架构重构计划

## 目标

推动代码仓库逐步收敛到目标职责分层，使宿主应用、通用 UI、插件实现和 core 契约各自承担清晰且稳定的责任。

## 目标原则

* 宿主应用是运行时外壳与组合根。

* `packages/ui` 是 Markdown 文档工作区核心前端实现层。

* Markdown 文档工作区本身的业务逻辑归属于 `packages/ui`。

* AI、任务管理以及未来新增能力的业务逻辑归属于各自插件。

* 宿主只暴露环境事实、能力句柄与 context，不基于这些事实直接完成业务判断。

* `packages/core` 只保留跨包最小稳定契约与宿主无关基础设施。

* 跨包消费者可以依赖插件公开 `api`，但不应依赖插件内部实现路径。

## 范围

本计划主要处理以下目录之间的包边界与职责收敛问题：

* `apps/*`

* `packages/core`

* `packages/ui`

* `packages/node`

* `packages/plugin-system`

* `plugins/ai-agent`

* `plugins/task-mgr`

## 阶段一：优先清理宿主中的业务逻辑

* 先扫描 `apps/*` 与 `packages/node` 中当前承载的业务判断、业务流程和领域状态流转。

* 将这些逻辑迁出宿主：

  * 属于 Markdown 文档工作区核心的，迁入 `packages/ui`

  * 属于 AI、任务或其他能力插件的，优先迁入对应插件

* 对于确实依赖宿主环境差异的行为，先把宿主中的业务分支改造成环境事实、能力句柄或 context 暴露，再由 `packages/ui` 或对应插件消费这些信息并完成判断。

* 先把宿主收缩为运行时环境接入、桥接接线、生命周期管理、运行时配置和插件装配层。

## 阶段二：明确 `packages/ui` 与插件的阶段性承接边界

* 保持 `packages/ui` 聚焦于 Markdown 文档工作区核心前端实现、视图容器、可复用组件和扩展点渲染。

* 明确允许 `packages/ui` 保留文档树、节点选择、文档打开/编辑/保存等核心工作区业务逻辑。

* 明确 AI 与任务相关逻辑的目标归属仍是对应插件，但允许在过渡阶段存在 `packages/ui -> 插件公共 api` 的依赖。

## 阶段三：将仍滞留在 `packages/ui` 的插件业务逻辑回收到插件

* 继续识别当前仍留在 `packages/ui` 中、但本质上属于 AI 或任务插件的业务 store、workflow、领域状态流转。

* 逐步把这些逻辑迁回各自插件，避免 `packages/ui` 继续成为插件业务的长期宿主。

* 在迁移过程中保持 `packages/ui` 对插件公共 `api` 的有限依赖，但避免新增新的插件业务沉积。

## 阶段四：建立并收紧插件公共 API

* 为 `plugins/ai-agent` 和 `plugins/task-mgr` 建立清晰、显式的公共 `api` 入口。

* 公共 `api` 只暴露宿主装配、跨进程桥接和跨包消费真正需要的稳定契约。

* 在宿主业务逻辑已迁出的前提下，再清理非插件代码对 `plugins/*/src/*` 的直接依赖。

## 阶段五：迁移领域契约并收缩 `packages/core`

* 将 AI 和任务领域模型从 `packages/core` 中移出。

* 将宿主、Node、Server、UI 等消费者逐步改为依赖插件公共 `api`，而不是继续依赖 `core` 中承载的领域契约。

* 仅保留文档工作区、插件系统和共享基础设施真正需要的最小契约。

* 收紧 `packages/core` 的 barrel exports，避免其继续充当领域杂糅的统一入口。

## 阶段六：重新梳理上下文与工作区边界

* 重新审视 `IContextProvider`、工作区上下文类型以及插件 contribution 上下文类型。

* 将当前过宽的领域所有权替换为必要且最小的宿主侧或工作区侧契约。

* 在保留文档工作区核心能力位于 `core` 的前提下，把领域语义逐步回收到插件。

## 阶段七：验证与收口

* 重新扫描 import 关系，确认目标依赖 DAG 得到满足。

* 重新执行 lint、类型检查、包构建以及受影响宿主和插件的定向回归验证。

* 在发生实质性边界变化时，同步更新架构文档与相关设计文档。

## 验证要求

* 任何阶段性重构完成后，都应同时验证“依赖边界是否收紧”和“现有功能是否保持可用”。

* 文档更新应与代码边界调整同步进行，避免文档原则与实际实现持续偏离。
