## **一、我的需求理解**

1. **摘要维护机制**：系统通过监听“文件保存”动作（无论是用户手工输入触发的 Save，还是确认 AI 修改后触发的 Merge & Save），自动在后台调用 LLM 更新该文件的摘要，保持上下文索引的时效性。
2. **文档结构与演进**：Q（问题与背景）和 A（方案）存放在同一个 Markdown 文件中。随着对话的深入，用户不断提出新条件，AI 不断给出新解答，因此 AI 可以在生成的变更计划中同时修改/追加 Q 和 A。
3. **柔性约束**：Q\&A 模型是用户的最佳实践“约定”，而非系统底层的“强校验限制”。系统本质上还是处理 Markdown 文件的块级合并。

## **二、产品经理视角的评估与质疑**

目前产品逻辑已经没有明显的断层，但我从工程落地和用户体验体验的边界，提出最后的推演：

**1. 评估：保存即触发摘要的“并发与状态叠加”问题**

* **推演**：如果用户在短时间内频繁按 `Ctrl+S`，或者连续 Approve 了好几个段落的变更，会触发多次“保存”动作。
* **挑战**：你需要设计防抖（Debounce）机制，或者使用队列来处理摘要更新请求。同时，在摘要更新的这段时间（可能长达数秒），如果用户立刻向 Agent 提问，系统使用的是旧摘要还是挂起等待？工程上需要处理这种中间状态，避免上下文错乱。

**2. 评估：“共同修改 Q 和 A”对 Prompt 带来的压力**

* **推演**：因为没有强格式限制，AI 需要通过 Prompt 理解“哪里是用户的背景提问，哪里是我之前给的方案”。
* **挑战**：当你在聊天框输入“再加一个条件，我不买美股”，AI 需要足够聪明，知道在文档的 Q 区域追加这个条件，并在 A 区域修改方案。这极其依赖底层模型的能力（如 Claude-3.5-Sonnet）和系统 Prompt 的设计。

## **三、关键风险与待确认项**

1. **后台静默失败风险**：摘要生成是异步操作，如果因网络问题或 API 限制导致摘要生成失败，用户在前端可能无感知，从而导致后续 Agent 调取的上下文不准。系统需要有轻量级的状态指示器（如：文件列表旁边的“摘要同步中/失败”小图标）。
2. **待确认**：在研发阶段，需要确立 Markdown “按段落 Diff”的具体算法（例如基于 AST 解析，还是简单的双换行符正则分割），这将直接决定合并体验的流畅度。

# **需求讨论文档：JARVIS 协同空间 (V1.1 最终确认版)**

## **1. 需求概述**

JARVIS 是一个人机共同编撰 Markdown 文档的协作空间。通过树形目录（问题域）绑定专属 Agent，以系统维护的文件摘要和手动 `@` 机制进行精准上下文路由。人机双方基于“问题(Q)-方案(A)”的约定模式，通过对话沟通和块级 Diff 合并，持续演进知识与方案。

## **2. 背景与问题**

* 传统 AI 助手缺乏长期上下文，难以针对特定领域的复杂问题持续推演。
* 用户真正需要的不是泛泛的“文本编辑”，而是基于背景约束下的“问题解决”。我们需要一个介于纯净笔记（Obsidian）和复杂 IDE（Cursor）之间，专用于沉淀思想和高层方案的协同框架。

## **3. 核心目标**

* 打造以“问题域”为边界的个人专属 AI 协同环境。
* 跑通“问题输入 -> 动态上下文检索 -> 方案拟定 -> 块级合并”的人机共创飞轮。

## **4. 目标用户 / 相关角色**

* **目标用户**：需管理复杂上下文、多线程规划工作与生活的知识工作者（如资深开发者）。
* **人类**：背景信息的提供者、AI 提案的决策者（Review & Merge）、系统的最终掌控者。
* **Agent**：特定问题域的顾问、跨文件上下文的检索者、变更计划（Patch）的提供者。

## **5. 核心产品逻辑**

1. **空间与 Agent 绑定**：树形目录即问题域，通过选择目录直接绑定 Agent 配置（Prompt）。
2. **柔性 Q\&A 约定**：同一 Markdown 文件中包含问题背景（Q）和解决方案（A）。随着交互深入，人机可共同对 Q 和 A 进行追加或修改。
3. **上下文智能组装**：

* 用户提问时，可手动 `@特定文件` 强制引入。
* Agent 获取目录文件树与**最新摘要**，自主决定调取其他相关文件。
* 组装“活跃文档 + `@`文档 + 智能检索文档”形成完整 Context。

1. **对话与 Diff 合并机制**：

* AI 在对话流中输出观点，并针对 Active 文档生成基于“段落/块（Block）”的变更计划。
* 用户在视图中查阅差异，执行确认（Accept/Reject）合并入文档。

1. **摘要自动化流转**：

* 任何形式的文档落盘（手动保存、确认合并后保存）均触发异步后台任务，调用 LLM 重新生成该文档的全局摘要，以维持后续检索的准确性。

## **6. 已确认结论**

* **形态定位**：非任务执行系统，而是文本层面的知识产出中枢。
* **文档形态**：统一采用 Markdown 格式，以段落为单位进行差异比对。
* **灵活度倾斜**：Q\&A 结构作为用户习惯约定，系统层面不作强校验，给予 AI 充分的重构和补充自由度。
* **闭环触发器**：明确了“文档保存”作为系统底层摘要刷新的统一生命周期钩子。

## **7. 待确认问题**

* **Diff 颗粒度算法**：前端渲染和对比时，按 Markdown 块切割的具体技术实现方案待工程预研。

## **8. 合理性质疑与风险**

* **并发状态管理**：连续的高频修改与保存可能导致摘要生成任务堆积或状态冲突，需引入防抖或队列机制。
* **长文本更新盲区**：若文件过长，由于大模型的注意力机制问题，AI 在重构 A（方案）时可能遗漏对 Q（背景）部分的同步更新，需要用户在 Review 时仔细把关。
* **异步失败处理**：摘要更新属后台行为，若网络异常导致失败，系统需有兜底策略或 UI 提示，防止 AI 使用过时摘要工作。

## **9. 竞品与差异化分析**

* 避开了 Obsidian 侧重网状链接的重度知识库方向，也避开了 Cursor 处理代码 AST 树的复杂工程。
* JARVIS 的核心切入点是**“问题域管理 + 纯自然语言/Markdown 的智能块级协作”**，填补了长文本与方案推演领域的 AI 深度协同空白。
