# 外部历史 Provider 搜索方案

## 摘要

- 本次只实现两个外部历史 provider 的搜索导入能力：
  1. `chatgpt-web`
  2. `gemini-web`
- 搜索框采用“共享同一份关键词状态”的方案：
  - ChatGPT 与 Gemini 复用同一个搜索框组件和同一份 query
  - 用户切换 provider 时，输入框中的关键词不变
  - 当前列表结果始终根据“当前 provider + 当前 query”重新加载
- `external-file` 保持现状，不显示搜索框，也不接入搜索态。
- 本次仍不实现分页读取所有聊天记录；空关键词只回到各 provider 的最近会话列表。

## 目标交互

### 1. ChatGPT 与 Gemini 共享同一个搜索关键词入口

在“外部”来源下：

- 选择 `ChatGPT` 时，左侧列表上方显示搜索框
- 选择 `Gemini` 时，左侧列表上方显示同一个搜索框组件
- 选择 `外部文件导入` 时，不显示搜索框

搜索框交互统一：

- 输入关键词
- 按 `Enter` 或点击搜索按钮触发查询
- 点击清空按钮后恢复该 provider 的最近会话列表

状态规则：

- ChatGPT 与 Gemini 共享同一份 query
- 用户从 `chatgpt-web` 切到 `gemini-web` 时，输入框保留原来的关键词
- 系统基于新的 provider 和同一个 query 重新加载结果列表

### 2. 空关键词返回最近会话

统一规则：

- `query = ''` 时，不展示“请输入关键词”的空态
- 而是直接回到该 provider 当前的最近会话列表

这样用户可以：

- 先搜索某个旧会话并查看结果
- 清空搜索词
- 立刻回到该 provider 的最近会话列表

### 3. 搜索结果仍走现有预览 / 导入链路

无论列表是“最近会话”还是“搜索结果”，点击条目后的行为保持一致：

- 加载详情
- 在右侧 `NormalChatView` 进入只读预览态
- 点击导入后保存为本地会话
- 切回本地活动态继续聊天

## 核心接口调整

### 4. `IHistoryProvider` 支持查询参数

当前 `IHistoryProvider` 只有：

- `getHistoryList(): Promise<ConversationHistorySummary[]>`
- `getHistoryDetail(externalId: string): Promise<Conversation>`

本次改为：

- `export interface HistoryListQueryOptions { query?: string }`
- `getHistoryList(options?: HistoryListQueryOptions): Promise<ConversationHistorySummary[]>`

含义：

- 不新增第二个搜索接口
- 历史列表查询继续统一走 `getHistoryList(...)`
- 空 query 表示“最近列表”
- 非空 query 表示“搜索结果”

这样 UI 与 store 不需要关心 provider 底层是接口搜索、页面原生搜索还是 DOM 搜索。

### 5. `ExternalHistoryProviderEntry` 声明搜索能力

为避免 UI 写死 provider 名称，`ExternalHistoryProviderEntry` 增加 capability：

- `features?: { historySearch?: boolean; historySearchPlaceholder?: string }`

约定：

- `chatgpt-web`
  - `historySearch: true`
  - placeholder 示例：`搜索 ChatGPT 聊天记录`
- `gemini-web`
  - `historySearch: true`
  - placeholder 示例：`搜索 Gemini 聊天记录`
- `external-file`
  - 不声明 `historySearch`

侧边栏只根据 capability 判断是否显示搜索框，不再写死 `providerId === 'gemini-web'` 之类判断。

## UI / Store 设计

### 6. 搜索框组件与关键词状态共享

建议新增复用组件：

- `packages/ui/src/components/ExternalHistorySearchBox.vue`

组件职责：

- 渲染输入框
- 渲染清空按钮
- 渲染搜索按钮
- 展示 loading / disabled 态

组件不持久化业务状态，只通过 props / emits 工作。

### 7. `chatStore` 改为维护共享 query 与当前 provider 结果

当前 store 只有一份：

- `externalHistoryItems`
- `isExternalHistoryLoading`
- `currentHistoryErrorCode`

这不适合承载“共享 query + provider 切换重查”的搜索流。

本次建议新增：

- `externalHistoryQuery: string`
- `externalHistoryQuerySubmitted: string`

建议的方法：

- `setExternalHistoryQuery(query: string): void`
- `submitExternalHistoryQuery(query?: string): Promise<void>`
- `clearExternalHistoryQuery(): Promise<void>`
- `loadExternalHistory(providerId?: ExternalHistoryProviderId, options?: HistoryListQueryOptions): Promise<void>`

行为约束：

- `externalHistoryQuery` 表示输入框当前值
- `externalHistoryQuerySubmitted` 表示最近一次真正提交给 provider 的关键词
- 切换 `activeExternalProviderId` 时，如果当前 query 非空，自动以同一个 query 对新 provider 重新加载
- 清空搜索会清空共享 query，并让当前 provider 回到最近列表
- `external-file` 不参与搜索，也不消费共享 query

### 8. 侧边栏只展示一份搜索框，但根据当前 provider 决定是否启用

修改：

- `packages/ui/src/components/ConversationSidebar.vue`
- `packages/ui/src/views/ConversationWorkspaceView.vue`

侧边栏在外部历史区域只渲染一份搜索框。当前 provider 支持搜索时显示并可用，不支持搜索时隐藏。

新增 props 建议：

- `externalHistoryQuery`
- `showExternalHistorySearch`
- `externalHistorySearchPlaceholder`
- `externalHistorySearchLoading`

新增事件建议：

- `update-external-query`
- `submit-external-query`
- `clear-external-query`

这样看起来和实现上都只有一个搜索框组件实例，query 由工作台共享持有；列表结果则随当前 provider 切换而刷新。

## ChatGPT 搜索实现

### 9. `ChatGPTWebProvider` 增加搜索能力

修改：

- `packages/core/src/providers/model/ChatGPTWebProvider.ts`

签名：

- `getHistoryList(options?: HistoryListQueryOptions): Promise<ConversationHistorySummary[]>`

建议新增私有方法：

- `private searchHistoryList(query: string): Promise<ConversationHistorySummary[]>`

行为：

- `query` 为空时：
  - 保持现有最近列表逻辑
  - 继续读取最近 28 条会话
- `query` 非空时：
  - 走 ChatGPT 的原生搜索能力
  - 将结果统一标准化为 `ConversationHistorySummary[]`

要求：

- 返回结构继续包含：
  - `id`
  - `title`
  - `updatedAt`
  - `origin: 'chatgpt-web'`
- 详情加载仍继续使用现有 `getHistoryDetail(externalId)` 链路

实现策略：

- 优先使用稳定的 request-based 搜索路径
- 如果实现阶段确认当前宿主抽象下无法直接走 request-based 搜索，再评估是否需要页面原生搜索桥接
- 但无论底层实现如何，对 UI / store 暴露的都只有：
  - `getHistoryList({ query })`

### 10. ChatGPT 搜索结果语义

对 UI 来说，ChatGPT 搜索结果与最近列表没有区别：

- 都渲染为左侧历史条目
- 都可点击预览
- 都可导入

对 provider 来说，需要保证：

- 搜索结果排序与 ChatGPT 原生结果保持一致
- 空结果返回空数组，不伪造兜底列表
- 失败时继续抛出可读异常，不把原始底层结构暴露到 UI

## Gemini 搜索实现

### 11. Gemini 继续沿用 bridge 架构

Gemini 不新增第二套实现，继续基于当前共享架构：

- core 层：`GeminiDomHistoryProvider`
- desktop：隐藏受控页 + preload bridge
- extension：content script bridge

修改文件：

- `packages/core/src/providers/history/gemini/GeminiHistoryBridge.ts`
- `packages/core/src/providers/history/gemini/GeminiDomHistoryProvider.ts`
- `packages/core/src/providers/history/gemini/geminiContentProtocol.ts`
- `apps/desktop/main/GeminiHistoryPageBridge.ts`
- `apps/desktop/main/gemini-history.preload.ts`
- `apps/extension/entrypoints/gemini-history.content.ts`
- `apps/server/src/provider-configs/gemini-history.json`
- `packages/core/src/interfaces/ProviderRemoteConfig.ts`

签名调整：

- `GeminiHistoryBridge.getHistoryList(config, options?: HistoryListQueryOptions): Promise<GeminiContentHistorySummary[]>`
- `GeminiDomHistoryProvider.getHistoryList(options?: HistoryListQueryOptions): Promise<ConversationHistorySummary[]>`
- `GeminiContentRequest` 增加：
  - `query?: string`

### 12. Gemini 搜索通过页面原生搜索框驱动

Gemini 的搜索逻辑仍在页面上下文内完成。

建议在 preload / content script 中新增：

- `applyHistorySearchQuery(config: GeminiHistoryRemoteConfig, query?: string): Promise<void>`
- `waitForHistorySearchSettled(config: GeminiHistoryRemoteConfig, query?: string): Promise<void>`

非空 query 的执行顺序：

1. 定位搜索输入框
2. 清空旧 query
3. 输入新 query
4. 触发回车或点击搜索按钮
5. 等待结果列表稳定
6. 调用现有列表抽取逻辑返回摘要

空 query 的执行顺序：

1. 清空搜索输入
2. 等待页面恢复最近列表
3. 调用现有列表抽取逻辑返回摘要

### 13. Gemini 搜索 selector 进入远程配置

为了避免把搜索 DOM 硬编码到代码中，`GeminiHistorySelectors` 增加可选字段：

- `historySearchInput?: string`
- `historySearchSubmit?: string`
- `historySearchClear?: string`
- `historySearchResultItem?: string`

`apps/server/src/provider-configs/gemini-history.json` 同步补上这些配置。

约定：

- 如果 `historySearchResultItem` 未配置
  - 默认回退到现有 `historyListItem`
- 搜索相关 selector 缺失时
  - 应返回标准化错误
  - 不能悄悄退化成错误的最近列表

### 14. Gemini 搜索错误处理

Gemini 搜索仍复用现有错误码：

- `AUTH_REQUIRED`
- `CONFIG_UNAVAILABLE`
- `SELECTOR_MISMATCH`
- `DETAIL_NOT_FOUND`
- `TAB_UNAVAILABLE`

关键原则：

- 未登录不能误报成“无搜索结果”
- 搜索输入框失配不能误报成“空列表”
- 页面未稳定时不能直接抽取旧列表结果

## 风险与权衡

### 26. provider 级状态复杂度上升

问题：

- store 从“只有列表状态”升级为“共享 query + provider 切换自动重查”

处理：

- 把 query 状态限制为一份共享字段
- 继续复用现有外部历史列表状态，避免为每个 provider 建一套缓存结构

### 27. ChatGPT 搜索实现路径不确定

问题：

- ChatGPT 搜索可能不是和最近列表完全相同的请求路径

处理：

- 对外接口先统一
- 底层搜索能力封装在 `ChatGPTWebProvider` 内部
- UI / store / 代理协议不依赖实现细节

### 28. Gemini 搜索 DOM 更脆弱

问题：

- Gemini 搜索入口和结果 DOM 可能比最近列表更容易变化

处理：

- 搜索 selector 放入远程配置
- preload / content script 增加关键阶段日志：
  - 输入框命中
  - query 提交
  - 结果条数

## 假设与默认项

- 本次只实现 `chatgpt-web` 与 `gemini-web`
- 搜索框组件与关键词状态共享
- ChatGPT 与 Gemini 切换时，沿用同一个 query 对当前 provider 重新查询
- 空关键词统一回到当前 provider 的最近会话列表
- `external-file` 不参与搜索
- 本次不实现分页读取全部历史记录
