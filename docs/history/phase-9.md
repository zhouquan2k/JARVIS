ChatPrizm 多源历史记录接入与架构设计文档
一、 需求背景与产品目标
1. 业务定位
ChatPrizm 致力于成为重度 AI 对话使用者的个人知识管理 (PKM) 中心。用户需要不仅能与多模型对比对话，还能将散落在各处的历史对话（如 ChatGPT、Gemini 官网）收拢、提纯并沉淀到本地。

2. 核心目标

极速切换的 UI 体验：采用顶层 Panel 平铺设计，让用户在一键之间切换不同的历史数据源。

高内聚低耦合的架构：UI 组件不关心底层数据来源，依靠统一的抽象接口进行数据通信。

低维护成本的外部接入：针对前端反爬极其严苛的 Gemini，采用“云端配置驱动的 DOM 抓取”方案，确保 Google 界面变更时插件无需重新发版即可自我修复。

二、 用户交互与 UI 设计 (UI/UX)
为了兼顾“一键切换的爽快感”和“PKM 本地为主的产品心智”，顶部导航栏采用带有视觉主次分组的顶层 Panel 设计。

1. 顶部数据源控制栏 (Top Panel)
在页面的左上角或正上方，设计一个横向的 Tab 切换栏，由本地区域、视觉分割线和外部导入区组成：

本地区域 (绝对 C 位)：处于最左侧或最显眼位置，辅以常驻的高亮或加粗样式。它代表用户在 ChatPrizm 中的“数字大脑主干”。

视觉分割线 (Divider)：使用一条柔和的竖线将“本地”与“外部导入源”隔开，建立物理边界感。

外部导入区 (平铺展示)：将当前高频支持的 Provider（ChatGPT, Gemini）直接平铺，点击即切换下方列表。超出的提供方可以收纳进“更多”下拉菜单。

2. 主从视图状态机 (Master-Detail View)
状态 A：本地活跃模式 (Active Mode)

触发：顶部 Panel 选中本地知识库。

行为：左侧列表显示本地存储的对话。右侧主视图允许用户在历史上下文中继续提问、发起多模型对比。

状态 B：外部预览与导入模式 (Preview & Import Mode)

触发：顶部 Panel 选中外部模型源（如 ChatGPT 或 Gemini）。

行为：左侧列表展示远端抓取到的历史摘要。点击单条后，右侧主视图复用聊天渲染组件，但处于全局只读状态。

导入动作：主视图底部原本的输入框被替换为悬浮导入按钮。点击导入后，数据落库，UI 自动切换回状态 A，用户可无缝衔接继续对话。

三、 核心抽象与工厂架构 (Core Architecture)
为了支撑顶层 Panel 的随意切换，系统引入了抽象接口与工厂模式来动态装配数据提供方。

1. 统一接口抽象
所有外部数据源必须实现统一的 IHistoryProvider 接口。该接口规定了获取历史摘要列表和获取单条对话详情的标准方法。无论底层是通过 API 逆向还是 DOM 抓取，最终吐出给 UI 的数据格式必须是绝对一致的标准对话数组。

2. 动态调度工厂
UI 层在切换顶层 Tab 时，绝不直接实例化具体的抓取类。而是将当前激活的 Tab 标识（如 'chatgpt' 或 'gemini'）传递给一个全局的 Provider 工厂。由工厂负责返回对应的实例实例，UI 层仅负责调用该实例的标准方法并渲染结果。这使得 UI 层与底层数据获取逻辑彻底解耦。

四、 Gemini 插件接入专项设计 (Config-Driven DOM Scraper)
鉴于 Gemini 内部 RPC 接口逆向难度大且极易被风控拦截，我们采用云端配置驱动的 DOM 抓取 (Remote Config-Driven Scraping) 路线。

1. 架构运作机制
整个抓取链路将核心选择器与插件代码剥离：

云端规则维护：在 ChatPrizm 服务端维护一个描述抓取规则的 JSON 配置文件。

规则拉取：插件启动或用户切换到 Gemini Tab 时，后台脚本拉取该配置文件。

隐式注入与抓取：若用户未打开 Gemini，后台静默打开 Gemini 官网标签页并注入通用的内容脚本。该脚本拿到云端规则后，执行 DOM 提取并清洗文本，最终组装为标准数据发回 UI 层。

2. 云端规则契约设计 (Schema)
云端下发的 JSON 配置中需包含明确的版本号、目标匹配网址，以及一个包含各种 CSS 选择器的字典对象。这个字典需定义：历史列表容器、列表单项、标题、链接、聊天气泡容器、用户提问气泡、AI 回答气泡以及用于触发自动向下滚动的懒加载元素选择器。
如果 Google 更改了前端 UI 导致选择器失效，开发团队只需在服务器上更新这些规则字段，用户的插件即可在下一次拉取时满血复活。

3. 优雅降级与异常处理
引擎在执行抓取前会进行健康检查。如果在页面上根据规则连续找不到核心的 DOM 节点，系统将判定网页结构已发生重大变更。此时抓取引擎会立即阻断执行并向 UI 层抛出规范化的异常，UI 层捕获后向用户展示友好的兜底提示文字，引导用户稍后再试或改用本地文件导入，避免插件直接崩溃死机。

五、 核心开源工程参考指南
为了实现前端的 DOM 抓取器，强烈建议参考以下唯一的综合性开源工程，它可以帮你解决 80% 的工程细节问题：

重点参考项目：farhandigital/gemini-history-manager

推荐理由：这是一个基于 TypeScript/JavaScript 构建的，专门针对 Gemini 对话记录捕获与管理的浏览器插件扩展项目。它不仅业务目标与你的需求高度重合，而且完全采用了本地优先（Local-First）的架构理念。

核心参考价值：

DOM 监听机制：它的源码清晰展示了如何使用 MutationObserver 绕过复杂的 API 请求，直接在页面底层监听 DOM 树的变动，静默获取实时更新的聊天标题和链接。

结构解析与本地化：提供了将混淆的网页聊天气泡提取、清洗并转换为结构化数据，进而安全存入浏览器本地存储的完整示例链路，是你构建 GeminiDOMHistoryProvider 提取层的最佳源码对照。
