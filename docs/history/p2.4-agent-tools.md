# Agent Tools 下一步实现计划

## 目标

下一步在现有 Gemini API Agent 最小闭环基础上，补齐可共享的工具调用能力。

本阶段目标：

- 工具能力由不同 agent 实现共享，而不是绑定在 `GeminiApiProvider`
- 保持 `AgentRuntime` 负责整体编排
- 引入独立的工具执行组件，负责工具声明解析与工具调用执行
- 文件类工具直接复用知识工作区 `IContextProvider`
- 新增以下 4 个内置工具：
  - `read_current_file`
  - `list_directory`
  - `read_file`
  - `search_in_scope`

---

## 分层结论

### 1. `AgentRuntime` 继续负责整体编排

`AgentRuntime` 的职责保持不变，仍然负责：

- 选择 provider
- 触发原生 agent 请求
- 接收 provider 返回的 `toolCalls`
- 维护多轮 tool loop
- 将工具结果回填给 provider

`AgentRuntime` 不直接内嵌每个工具的具体实现细节。

### 2. 新增 `AgentToolExecutor`

新增独立的 `AgentToolExecutor`，作为 `AgentRuntime` 的内部依赖。

它只负责两件事：

- 根据当前 `ResolvedAgentConfig.tools` 解析本次请求允许暴露给模型的工具声明
- 执行 provider 返回的单次 `toolCall`，并包装为 `AgentToolResult`

它不是第二个 runtime，也不负责 provider 路由。

### 3. 工具定义使用 `AgentToolDefinition`

每个工具使用统一的静态定义对象表达：

- `id`
- `description`
- `inputSchema`
- `execute()`

这样可以把工具的 schema 和执行逻辑收拢在一起，避免散落在 runtime 中。

### 4. 直接复用 `IContextProvider`

不新增 `AgentWorkspaceAccess` 之类的额外抽象。

文件类工具直接复用已有知识工作区能力：

- `listTree`
- `readDocument`
- `resolveScopedAgentConfig`

同时在 `IContextProvider` 中补充搜索接口：

- `searchInScope`

本阶段不做 fallback。

如果某个宿主未实现 `searchInScope`，则 `search_in_scope` 直接返回“暂不支持”错误。

## 接口设计

### `AgentToolDefinition`

```ts
export interface AgentToolDefinition<TArgs = Record<string, unknown>, TResult = unknown> {
  id: string;
  description: string;
  inputSchema: Record<string, unknown>;
  execute(args: TArgs, context: AgentToolExecutionContext): Promise<TResult>;
}
```

### `AgentToolExecutionContext`

```ts
export interface AgentToolExecutionContext {
  agent: ResolvedAgentConfig;
  activePath: string | null;
  contextProvider: IContextProvider;
}
```

### `AgentToolExecutor`

```ts
export interface AgentToolExecutor {
  resolveTools(agent: ResolvedAgentConfig): Array<{
    id: string;
    description: string;
    inputSchema: Record<string, unknown>;
  }>;
  execute(call: AgentToolCall, context: AgentToolExecutionContext): Promise<AgentToolResult>;
}
```

### `IContextProvider` 扩展

```ts
export interface ContextSearchRequest {
  query: string;
  maxResults?: number;
}

export interface ContextSearchMatch {
  path: string;
  line: number;
  column: number;
  preview: string;
}

export interface IContextProvider {
  id: string;
  initializeAccess(): Promise<void>;
  getContext(): Promise<WorkspaceContext>;
  readDocument(path: string): Promise<ContextDocument>;
  writeDocument(input: WriteContextDocumentInput): Promise<void>;
  createNode(input: CreateContextNodeInput): Promise<ContextNode>;
  searchInScope(request: ContextSearchRequest): Promise<ContextSearchMatch[]>;
}
```

### `AgentRunRequest` 扩展

Provider 不直接读取 `agent.tools` 生成 function declarations，而是读取运行时已解析好的工具声明：

```ts
export interface AgentRunRequest {
  prompt: string;
  agent: ResolvedAgentConfig;
  context?: { parentMessageId?: string; conversationId?: string };
  modelId?: string;
  attachments?: MessageAttachment[];
  history?: ProviderContextMessage[];
  modelOptions?: Record<string, boolean>;
  toolExchanges?: AgentToolExchange[];
  tools?: Array<{
    id: string;
    description: string;
    inputSchema: Record<string, unknown>;
  }>;
}
```

### `AgentRuntimeRequest` 扩展

运行时需要拿到当前知识工作区上下文：

```ts
export interface AgentRuntimeRequest {
  prompt: string;
  agent: ResolvedAgentConfig | null;
  providerId?: string;
  modelId?: string;
  attachments?: MessageAttachment[];
  history?: ProviderContextMessage[];
  modelOptions?: Record<string, boolean>;
  context?: { parentMessageId?: string; conversationId?: string };
  workspace?: {
    activePath: string | null;
    contextProvider: IContextProvider | null;
  };
}
```

## 内置工具

### `read_current_file`

用途：

- 读取当前知识工作区正在编辑或当前激活的文件

行为：

- 使用 `activePath`
- 若当前没有激活文件，则返回明确错误

### `list_directory`

用途：

- 列出指定目录下的文件和目录

行为：

- 输入目录路径
- 调用 `contextProvider.getContext()` 后在内存树中过滤目标目录的直接子节点

### `read_file`

用途：

- 读取指定文件内容

行为：

- 输入文件路径
- 调用 `contextProvider.readDocument(path)`

### `search_in_scope`

用途：

- 在当前 agent 作用域内搜索文件内容

行为：

- 不接受 `scope` 参数
- 搜索范围由 `agent.scopePath` 决定
- 调用 `contextProvider.searchInScope({ query, maxResults })`

说明：

- `scope` 是 `AgentConfig` 已定义的边界，不需要重复暴露给模型作为参数

### 文件修订工具

如果下一步需要支持类似 Codex / Copilot 的局部文件修订，而不是整文件重写，则工具设计应继续优先服务大模型使用，而不是优先追求接口合并。

本阶段建议新增以下文件修订工具：

- `replace_text_in_file`
- `replace_range_in_file`
- `insert_text_in_file`
- `delete_range_in_file`
- `write_file`

设计原则：

- 优先拆分成语义明确的工具，而不是做一个 `edit_file(mode=...)` 的万能工具
- `write_file` 只承担整文件创建或整文件覆盖
- 局部修订由 `replace / insert / delete` 这类原子编辑工具承担

原因：

- 工具是给大模型使用的，工具名本身就是强提示
- `replace_text_in_file` 比 `edit_file(mode="replace_text")` 更容易被模型稳定选择
- `insert_text_in_file` 比 `edit_file(mode="insert")` 更容易减少错参和漏参
- 在当前工具数量仍然有限的前提下，明确拆分比过度合并更有利于模型使用

### `write_file`

用途：

- 创建文件
- 整体覆盖文件内容

行为：

- 接收 `path`、`content`
- 使用模式字段区分创建与覆盖

建议输入：

```ts
type WriteFileInput = {
  path: string;
  content: string;
  mode: 'create' | 'overwrite' | 'create_or_overwrite';
}
```

### `replace_text_in_file`

用途：

- 用精确文本锚点替换文件中的目标片段

适用场景：

- 已知旧文本
- 需要保持其余结构不变

### `replace_range_in_file`

用途：

- 按行范围替换文件中的连续区域

适用场景：

- 已知具体起止行
- 需要对某个块进行局部重写

### `insert_text_in_file`

用途：

- 在指定行前或行后插入文本

适用场景：

- 增加 import、增加配置段、增加函数体片段

### `delete_range_in_file`

用途：

- 删除指定行范围

适用场景：

- 删除连续代码块或文档段落

### 文件修订与 `read_file`

如果后续要补充面向编辑的读取能力，可在现有 `read_file` 基础上支持可选行范围参数，但不单独把这一点作为本阶段核心目标。

原因：

- 当前阶段的关键是先把工具调用与局部编辑闭环建立起来
- 是否把 `read_file` 与 `read_file_range` 分离，可以放到具体实现阶段再视模型使用效果调整

## 文件 diff 与行级 undo/redo

本阶段如果支持文件修订，建议采用和 Codex / Copilot 更接近的模式：

- 工具执行时直接写盘
- 程序记录修改前后的文件内容
- UI 在展示 diff 时由程序计算行级 diff
- undo / redo 也由程序驱动，而不是让 LLM 生成补丁记录

### 不让 LLM 生成变更记录

LLM 不负责生成 `FileChangeRecord`、hunk 元数据或 diff 结构。

原因：

- LLM 更适合生成编辑意图
- 行号、变更块边界、重复片段定位等信息由程序计算更稳定
- 对于仅需行级 undo / redo 的场景，没有必要让模型承担 diff 元数据生成

### 程序记录 before / after

每次文件编辑工具执行时，由程序自动记录：

- `beforeContent`
- `afterContent`

最小记录模型如下：

```ts
type FileChangeRecord = {
  id: string;
  path: string;
  beforeContent: string;
  afterContent: string;
}
```

说明：

- 这不是让 LLM 生成的数据
- 而是工具执行成功后，由程序生成的变更记录

### diff 的计算方式

UI 展示 diff 时，不要求预先保存 diff 结果。

建议方式：

- 运行时只保存 `beforeContent` 和 `afterContent`
- 需要展示时，再由程序计算 line diff

这样可以：

- 简化记录模型
- 避免让工具层提前承担 diff 序列化格式
- 先满足当前的行级 diff 展示需求

### 行级 undo / redo

当前明确只需要行级 undo / redo。

因此本阶段建议：

- 不做复杂 patch 提案模型
- 不做 `propose_file_patch`
- 不做 `preview_patch`
- 不要求持久化保存 hunk 结构

最小实现方式：

- `undo` 时写回 `beforeContent`
- `redo` 时写回 `afterContent`

如果未来要支持更细粒度的局部撤销，再考虑在程序侧补充 hunk 级记录，而不是让 LLM 参与生成。

### undo / redo 职责分配

为保持边界清晰，`undo / redo` 建议按以下方式分层：

- `IContextProvider`
  - 只负责文件当前状态的读写
  - 不负责保存历史
  - 不提供 `undo()` / `redo()`
- `AgentToolExecutor`
  - 负责执行文件编辑工具
  - 编辑成功后，把 `beforeContent` / `afterContent` 交给变更服务记录
- `FileChangeService`
  - 负责维护每个文件的 undo stack / redo stack
  - 负责在 undo / redo 时调用 `contextProvider.writeDocument()`
  - 负责向 UI 暴露最近一次文件变更
- UI
  - 负责展示 diff
  - 负责触发 undo / redo

最小记录结构：

```ts
type FileChangeRecord = {
  id: string;
  path: string;
  beforeContent: string;
  afterContent: string;
}
```

最小流程：

- 编辑工具执行时：
  - 先读旧内容
  - 再写新内容
  - 最后记录 `FileChangeRecord`
- `undo` 时：
  - 写回 `beforeContent`
- `redo` 时：
  - 写回 `afterContent`

当前阶段建议先做内存态的 undo / redo，不要求持久化历史。

## `search_in_scope` 与未来 `search_internet` 的边界

未来如果要支持联网搜索，应新增独立工具：

- `search_internet`

不复用 `search_in_scope`。

原因：

- `search_in_scope` 面向知识工作区本地上下文
- `search_internet` 面向外部网络
- 两者的数据来源、权限、可信度、宿主依赖和结果结构都不同

因此：

- `IContextProvider` 只承载 workspace / local context 能力
- internet search 走独立能力线，不进入 `IContextProvider`

## 非目标

本阶段不做以下事项：

- 不引入完整的通用工具市场或插件体系
- 不引入 MCP 工具桥接
- 不实现 `search_internet`
- 不引入脚本执行能力
- 不为 `search_in_scope` 提供 fallback 扫描实现
- 不改动 `AgentConfig` 的声明式边界
- 不让 LLM 生成 diff、hunk 或 `FileChangeRecord`
- 不引入 `propose_file_patch` / `preview_patch` 预览式补丁流程

---

## 一句话总结

下一步的实现方案是：保留 `AgentRuntime` 作为唯一的 agent 编排层，新增 `AgentToolExecutor` 负责工具声明解析与工具调用执行，使用 `AgentToolDefinition` 统一表达内置工具；文件类工具直接复用 `IContextProvider` 并扩展必选的 `searchInScope` 接口，`search_in_scope` 的范围固定由 `agent.scopePath` 决定，不作为模型参数传入；如果进入文件修订场景，则继续优先提供对大模型更友好的明确编辑工具，工具直接写盘，由程序记录 `beforeContent` / `afterContent` 并在 UI 层计算 line diff 与支持行级 undo / redo，而不是引入补丁预览流程或让 LLM 生成变更记录。
