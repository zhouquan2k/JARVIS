## 5引入统一的接口暴露 / Bridge-RPC 抽象

### 当前问题

当前系统在多个宿主中都存在“上层使用 `IXXX`，下层实现 `IXXX`，中间手写桥接”的模式，但这种模式尚未被抽象成统一机制。

典型表现包括：

- Desktop 中：
  - `IContextProvider` 通过 `createDesktopContextProvider()` + preload bridge + `registerContextIpc(...)` 暴露
  - `IModelProvider` 通过 `DesktopProxyProvider` + `providerHost` 暴露
  - `IHistoryProvider` 通过 `DesktopHistoryProxy` + `providerHost` 暴露
- Extension 中：
  - `IModelProvider` 与 `IHistoryProvider` 通过 background proxy 暴露
- Web 中：
  - `IContextProvider` 通过 HTTP API 暴露

问题在于：

- 上层看起来都在消费统一接口
- 但中间“如何把接口暴露出去”的机制是按领域分别手写的
- 这会导致：
  - 桥接模式重复
  - 宿主差异散落
  - 新增 `IXXX` 时需要重新设计一套暴露方式

### 目标方向

目标应是统一成如下模式：

- 上层使用 `IXXX`
- 下层实现 `IXXX`
- 中间通过统一的 bridge / RPC 抽象完成跨环境转换

也就是说，不把“暴露 `IContextProvider`”当成特例，而是把它视为“暴露任意接口”的一种实例。

### 为什么这不仅适用于 Desktop，也适用于 Web / Extension

这个模式并不只适用于 Electron：

- `Desktop App`
  - 跨 renderer / preload / main
- `Browser Extension App`
  - 跨 page / background / content script
- `Web App`
  - 跨 browser client / HTTP server

它们虽然底层协议不同，但上层结构一致：

- 一端消费接口
- 一端实现接口
- 中间通过某种 transport / bridge 做转换

因此这一层抽象应该是跨宿主可复用的设计，而不是 Electron 专属技巧。

### 建议拆成 3 类桥接抽象

#### 1. Unary RPC Bridge

适合普通 request/response 语义的接口，例如：

- `IContextProvider`
- `IExternalConversationProvider`
- 未来其他纯查询/命令型接口

建议形态：

```ts
createUnaryProxy<T>(...)
registerUnaryHandlers<T>(...)
```

#### 2. Streaming RPC Bridge

适合带流式更新语义的接口，例如：

- `IModelProvider`

原因是这类接口除了 request/response，还包含：

- `requestId`
- 流式 update
- `done/error`
- `abort`

建议形态：

```ts
createStreamingProxy<T>(...)
registerStreamingHandlers<T>(...)
```

#### 3. Event Bridge

适合主进程/后台主动通知上层的场景，例如：

- 登录完成
- 登录窗口关闭
- 其他宿主事件

建议形态：

```ts
subscribeEvent(...)
publishEvent(...)
```

### 建议的抽象目标

最终不应继续写成：

- desktop 专用 context bridge
- desktop 专用 history proxy
- extension 专用 background proxy

而应逐步收敛成：

```ts
createUnaryProxy<IContextProvider>(...)
createUnaryProxy<IExternalConversationProvider>(...)
createStreamingProxy<IModelProvider>(...)
```

以及对应的 handler 注册机制：

```ts
registerUnaryHandlers<IContextProvider>(...)
registerUnaryHandlers<IExternalConversationProvider>(...)
registerStreamingHandlers<IModelProvider>(...)
```

### 职责边界

这层统一桥接抽象负责：

- 方法名与参数的转换
- 跨宿主 transport 封装
- 错误回传
- 对流式场景的 update / done / abort 处理

它不负责：

- 具体业务逻辑
- provider / context / history 的真实实现
- 会话数据模型本身

### 与已有重构项的关系

这一层桥接抽象，是以下命名/职责收敛后的自然下一步：

- `IConversationPersistProvider`
- `IExternalConversationProvider`
- `ModelProviderRuntime`
- `ConversationWorkflowController`

也就是说，前面的重构是在收敛“核心概念名”，而这一项是在收敛“这些概念如何跨宿主暴露”。

### 推荐实施顺序

建议按以下顺序推进：

1. 先完成核心命名收敛
   - `ModelProviderRuntime`
   - `IExternalConversationProvider`
   - `IConversationPersistProvider`
2. 再抽 `ConversationWorkflowController`
3. 最后再引入统一 bridge / RPC 抽象

原因是：

- 如果核心接口名还不稳定，桥接抽象也会跟着反复变化
- 先稳定核心接口，再抽统一暴露机制，风险更低

### 最小落地建议

第一阶段不需要一步做到“完全泛化”。

可以先做一个最小版本：

- 抽出一套通用 unary bridge 机制
- 优先替换：
  - Desktop `IContextProvider`
  - Desktop `IExternalConversationProvider`
- 等 unary 模式稳定后，再抽 streaming bridge，覆盖 `IModelProvider`

这样可以避免一开始就做成过重的“万能 RPC 框架”。
