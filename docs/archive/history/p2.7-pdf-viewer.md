# 文件工作区 Viewer 方案（首版落地 PDF）

## 摘要

- 目标不是只给知识工作区增加一个 PDF 特例，而是把中间主显示区升级为通用 `Document Viewer` 框架。
- 不同文件类型通过 `mimeType` 选择不同 viewer；viewer 自身声明可支持的 `mimeType` 以及 `view/edit` 能力。
- 系统维护统一的 `mimeType -> viewer` 注册关系，而不是在 store 或组件里继续堆 `.pdf`、`.md` 之类的特判。
- 首版只落地两个 viewer：
  - Markdown viewer：继续复用现有 Milkdown 编辑链路
  - PDF viewer：只读预览，优先使用宿主环境原生 PDF viewer，通过 Blob URL 内嵌显示

## 当前实现现状

### 1. 主显示区当前本质上仍是 Markdown 编辑器

当前中间栏主要由以下链路组成：

- `packages/ui/src/views/DocumentWorkspaceView.vue`
- `packages/ui/src/components/DocumentEditorPane.vue`
- `packages/ui/src/store/documentWorkspace.ts`
- `packages/ui/src/utils/markdownDocument.ts`

现状特点：

- `DocumentEditorPane` 只接收 `activePath` 和 `modelValue: string`
- 中间区域无论打开什么文件，都会尝试挂载 Markdown 编辑器
- `draftContent`、自动保存、diff、undo/redo 都围绕文本编辑设计

这意味着当前实现并没有真正的“文件查看器”概念，只有“Markdown 编辑器是否已挂载”。

### 2. ContextProvider 当前的 Document 语义仍然等同于文本

当前接口定义位于：

- `packages/core/src/interfaces/IContextProvider.ts`

当前 `ContextDocument` 仅包含：

- `path`
- `content`
- `updatedAt`
- `version`

当前 `IContextProvider` 仅提供：

- `readDocument(path: string): Promise<ContextDocument>`
- `writeDocument(path: string, content: string): Promise<void>`

这意味着：

- web / extension / desktop 三个宿主都默认“文件一定是 UTF-8 文本”
- renderer 拿不到统一的 `mimeType`
- renderer 拿不到统一的文件内容表达，无法自然支持二进制文件

### 3. 多宿主链路共享同一套 context 语义

现有宿主实现：

- web / extension：`HttpContextProvider -> /api/context/*`
- desktop：`preload -> IPC -> contextIpc`

相关文件：

- `packages/core/src/providers/context/HttpContextProvider.ts`
- `apps/server/src/routes/context.ts`
- `apps/server/src/providers/localFileContextProvider.ts`
- `apps/desktop/src/context/createDesktopContextProvider.ts`
- `apps/desktop/main/preload.ts`
- `apps/desktop/main/contextIpc.ts`

因此这次方案应该把共享接口升级成“通用用户文档”契约，而不是围绕 PDF 单独扩一条二进制旁路。

## 方案设计

### 4. 总体策略：树层保留 file/directory，内容层升级为通用 Document Viewer

本次建议做两层抽象，并统一命名口径：

- 树层：仍然保留 `file/directory` 节点，用于文件树导航、展开折叠和作用域选择
- 内容层：统一把可打开的用户数据抽象为 `document`
- 中间不再被定义为“编辑器”，而是“文档展示/编辑面板”
- 右侧 agent 仍然工作在当前文件/目录作用域上，但不再假设当前激活对象一定是文本 document

这里的含义是：

- `ContextNode.kind` 仍然是 `file | directory`
- `readDocument()` 返回的是更通用的用户文档，而不是“纯文本 document”
- viewer 根据 `mimeType` 决定如何展示或编辑该 document

这里的“去掉 Knowledge”主要指底层能力模型和工作区命名都统一收敛：

- provider 契约用 `Document`
- viewer 契约用 `DocumentViewer`
- store 状态用 `activeDocument`
- 工作区与组件命名统一为 `DocumentWorkspace` / `DocumentEditorPane`

这样做的原因：

- `Knowledge` 这个名字会让人继续把工作区理解为特定场景，而不是通用文档工作区
- 底层抽象已经改成 `Document`，继续保留 `KnowledgeXXX` 会造成概念分裂
- viewer、store、view、pane 统一命名后，后续新增文档类型时心智模型更一致

### 5. Viewer 体系：由 viewer 声明能力，由 registry 统一决策

核心原则：

- viewer 通过 `mimeType` 声明自己可以打开哪些文件
- viewer 自身声明是否支持 `view` / `edit`
- 系统通过统一 registry 维护 `mimeType` 与 viewer 的映射关系

建议引入的概念：

```ts
export interface DocumentViewerDefinition {
    id: string;
    supportedMimeTypes: string[];
    capabilities: {
        view: boolean;
        edit: boolean;
    };
}
```

示例：

- Markdown viewer
  - `supportedMimeTypes: ['text/markdown', 'text/plain']`
  - `capabilities: { view: true, edit: true }`
- PDF viewer
  - `supportedMimeTypes: ['application/pdf']`
  - `capabilities: { view: true, edit: false }`

统一 registry 负责：

- 给定当前 `file.mimeType` 解析应使用哪个 viewer
- 当多个 viewer 命中时按优先级决定
- 未命中时回退到 unsupported / empty 状态

这样做的原因：

- 后续新增图片、HTML、CSV、代码文件 viewer 时不需要继续修改 store 分支
- viewer 能力定义集中，不会散落在 UI 各层
- “文件能否编辑”可以从一开始作为能力模型明确表达

### 6. Provider 接口：保留 `readDocument/writeDocument`，但升级为通用用户文档语义

不建议继续把设计建立在：

- `readBinaryDocument()`

这类接口分裂上。原因是它本质上仍在区分“文本世界”和“PDF 特例”，对后续更多 viewer 并不通用。

更合适的方向是保留 `readDocument()/writeDocument()` 这组方法名，但把 `Document` 的定义改成通用用户文档：

```ts
export interface ContextDocument {
    path: string;
    mimeType: string;
    dataBase64: string;
    updatedAt?: number;
    version?: string;
    canWrite?: boolean;
}

export interface WriteContextDocumentInput {
    path: string;
    mimeType: string;
    dataBase64: string;
    expectedVersion?: string;
}

readDocument(path: string): Promise<ContextDocument>;
writeDocument(input: WriteContextDocumentInput): Promise<void>;
```

设计要点：

- `mimeType` 是统一入口，而不是让 UI 按扩展名分支
- 内容载荷统一为 `dataBase64`
- 文本 document 由对应 viewer/editor 负责按 UTF-8 等方式解码
- 二进制 document 由对应 viewer 直接按 `mimeType` 处理
- `canWrite` 明确表达 provider / 文件本身是否允许写入
- `writeDocument()` 是通用写入契约，但本期实现仍只要求文本写入；PDF 继续只读

为什么不保留 `readBinaryDocument()` 作为主方案：

- 名字本身仍然是 PDF / 二进制补丁思路
- 后续一旦支持图片、音频、Office 文件，接口会继续膨胀
- store 和上层 UI 仍会被迫知道“什么时候该调哪个读取函数”

为什么不再额外区分 `contentKind`：

- 当前已经用 `mimeType` 作为 viewer 决策入口
- 若协议层继续引入 `text/binary` 二分，会把内容模型再拆回两套
- 对 UI 来说，更简单的约束是“任何 document 都有 `mimeType + dataBase64`，viewer 自己决定如何消费”

### 7. Server / HTTP / Desktop IPC：继续走同一条 context 通道，但协议改成 File

涉及文件仍然是：

- `packages/core/src/providers/context/HttpContextProvider.ts`
- `apps/server/src/routes/context.ts`
- `apps/server/src/services/httpContextService.ts`
- `apps/server/src/providers/localFileContextProvider.ts`
- `apps/server/src/types/context.ts`
- `apps/desktop/main/contextIpc.ts`
- `apps/desktop/main/preload.ts`
- `apps/desktop/src/context/createDesktopContextProvider.ts`
- `apps/desktop/src/env.d.ts`

但协议口径改为通用 document：

- `readDocument(path: string)`
- `writeDocument(input)`

而不是额外新增一条 `readBinaryDocument` 旁路。

本期首版约束：

- provider 至少要能正确返回：
  - Markdown 文件的 `text/markdown + dataBase64`
  - PDF 文件的 `application/pdf + dataBase64`
- `writeDocument()` 首版仍只处理文本文件
- PDF 不支持写回

这样做的收益：

- Web / Desktop / Extension 继续共享一套抽象
- 未来增加新 viewer 时，宿主协议不需要重新开新方法名

### 8. Mock Provider 与测试基建也应切到 File 语义

涉及文件：

- `packages/core/src/testing/createMockContextProvider.ts`

mock 数据需要能够表达：

- `mimeType`
- `dataBase64`
- `canWrite`

目的：

- 支撑 store、viewer registry 和主面板组件测试覆盖不同文件类型

## UI 与状态改造

### 9. Store：先读取 Document，再解析 Viewer

涉及文件：

- `packages/ui/src/store/documentWorkspace.ts`

建议新增状态：

```ts
activeDocument: ContextDocument | null;
activeViewerId: string | null;
activeViewerCapabilities: {
    view: boolean;
    edit: boolean;
} | null;
activePaneMode: 'empty' | 'viewer' | 'unsupported';
```

主要改动点：

- `openNode(path: string): Promise<void>`
  - 先调用 `contextProvider.readDocument(path)`
  - 再根据 `document.mimeType` 通过 registry 解析 viewer
- `updateActiveFileContent(content: string)`
  - 仅当当前 viewer 支持 `edit` 且当前 document 可写时生效
- `flushActiveFile(): Promise<void>`
  - 仅在当前 document 对应的 viewer 支持编辑且当前 document 可写时生效
- `undoActiveFileChange()` / `redoActiveFileChange()`
  - 仅在可编辑文本 viewer 下生效

约束：

- 从脏的 Markdown 文件切到 PDF 时，仍然沿用现有逻辑先 flush 文本改动
- 只读 viewer 不参与自动保存、diff、undo/redo
- `activePath` 仍保留，用于右栏 agent 感知当前选中节点

### 10. 主视图参数传递：从 Editor Props 走向 Viewer Props

涉及文件：

- `packages/ui/src/views/DocumentWorkspaceView.vue`

改造方向：

- 传给中间面板的不再只是 `modelValue`
- 而是传当前 `activeDocument`、viewer 解析结果以及现有编辑状态

建议传递的信息包括：

- `activePath`
- `activeDocument`
- `activeViewerId`
- `activeViewerCapabilities`
- `isSaving`
- `latestFileChange`
- `diffEntries`
- `canUndo`
- `canRedo`

同时调整右栏 assistant 上下文：

- 右栏在会话首轮发送时，才根据当前 `activeDocument` 和 provider 可接受的 `mimeType` 判断是否自动采纳该文档
- 若当前文本文件被采纳，则其内容可作为首轮请求的 primary context
- 若当前 PDF 文件被采纳，则其内容 MUST 作为首轮请求附件发送，而不是把 `dataBase64` 当作正文文本
- 若 provider 不接受当前 `mimeType`，则该文档 MUST NOT 进入模型请求，只保留：
  - `activePath`
  - `contextProvider`
  - 文件元信息
- 后续 follow-up 默认只依赖历史消息重放，不再因为用户切换了工作区当前节点而自动替换或重复附加文档

原因：

- 避免 agent 把二进制内容误当作文本
- 保持右栏作用域绑定和文件工具能力不变
- 让会话上下文以“首轮真实发送了什么”为准，而不是以“当前 UI 选中了什么”为准

### 10.1 右栏上下文与历史保存原则

右栏请求在设计上应收敛到“真实请求回放”模型，而不是“每轮临时读取当前工作区状态”模型。

约束：

- 凡是实际进入某轮请求的内容，无论来自手动附件还是自动采纳的 `activeDocument`，都必须原样写回该轮 user message
- history 的职责不是近似还原聊天 UI，而是完整还原当时真实发给模型的内容
- 会话中的 follow-up 请求必须优先依赖历史重放，而不是再次根据当前工作区节点推断是否要补发旧文档
- 切换当前工作区节点不会 retroactively 改写已存在会话的上下文语义

职责边界：

- `AgentRuntime` 负责根据 provider 能力、当前文档和既有 history 组装“最终真实请求”
- `chat.ts` 负责基于该最终请求快照更新并持久化 `currentConversation.messages`
- provider 只负责把统一请求翻译成目标协议并发送，不直接决定本地会话历史如何落盘

### 11. 中间面板：`DocumentEditorPane` 作为通用文档面板

涉及文件：

- `packages/ui/src/components/DocumentEditorPane.vue`

`DocumentEditorPane` 的职责应调整为通用文档面板。

建议 props 方向：

```ts
activePath: string | null;
activeDocument: ContextDocument | null;
activeViewerId: string | null;
activeViewerCapabilities: {
    view: boolean;
    edit: boolean;
} | null;
modelValue?: string;
```

行为设计：

- `empty`
  - 展示空态文案
- `markdown viewer`
  - 保持现有 Milkdown 初始化、同步、销毁逻辑
- `pdf viewer`
  - 主动销毁 Milkdown 编辑器
  - 将 `dataBase64` 转成 Blob
  - 生成 Blob URL
  - 使用 `iframe` 或 `object` 渲染 PDF
- `unsupported`
  - 展示“当前文件类型暂不支持预览或编辑”的明确提示

资源管理：

- 文件切换时释放旧 Blob URL
- 组件卸载时释放 Blob URL
- viewer 切换时清理旧 viewer 资源

UI 行为：

- 只有支持 `edit` 的 viewer 才显示保存按钮和编辑态交互
- 只有可编辑文本 viewer 才显示 diff 面板和 undo/redo
- 空态文案更新为：
  - “从左侧文件树选择文件开始查看。支持的文件类型会自动选择对应 viewer。”

### 12. Viewer 解析优先级

建议采用如下优先级：

1. 优先按 `mimeType` 精确匹配 viewer
2. 若 provider 暂时无法稳定提供 `mimeType`，可临时以扩展名推断作为兜底
3. 若仍无法命中，则进入 unsupported 状态

说明：

- 扩展名推断只作为兼容兜底，不应成为主路径
- 真正的注册关系应建立在 `mimeType` 上

## 首版 PDF Viewer 落地范围

### 13. 本期只实现 PDF viewer，不实现通用 viewer 全家桶

本期的实际落地范围仍然保持克制：

- 支持 Markdown viewer
- 支持 PDF viewer
- 只读预览 PDF
- 不引入 `pdf.js`
- 不实现 PDF 编辑、批注、搜索、高亮、页缩略图或页码导航

换句话说：

- 设计先做成通用框架
- 实现先落一个 PDF viewer，验证框架方向正确

### 14. PDF 渲染方案选择

本次采用：

- 原生嵌入 PDF viewer
- Blob URL + `iframe` / `object`

不采用 `pdf.js` 的原因：

- 当前仓库没有现成 PDF 渲染依赖
- 当前需求仅为只读显示
- 首版优先以最小改动验证 File Viewer 架构是否可行

已知风险：

- web / desktop 一般可行
- extension 宿主下是否完全允许内嵌 `blob:` PDF，需要用真实 E2E 验证
- 若扩展环境受限，需要在同一面板提供兜底：
  - 显示“当前环境不支持内嵌 PDF 预览”
  - 提供“新标签打开 PDF”入口

## 默认边界

- 首版只落地 `application/pdf` 的 viewer
- 设计上改为通用 `Document + viewer registry`
- 实现上仍只提供 PDF 只读预览
- 不改变现有 Markdown 编辑体验
- 不让 PDF 内容进入右栏 agent 的主文本上下文
- 自动采纳当前文件只发生在会话首轮；后续若要引入新文件，应由用户显式添加

## 迁移建议

- 先统一 provider 与 store 的能力模型，建立“通用 `readDocument/writeDocument` + viewer registry”
- 再让 Markdown viewer 和 PDF viewer 接到同一套主面板协议
- 然后收敛右栏请求模型：首轮自动采纳、真实请求写回 history、后续按 history 重放
- 最后统一完成 `KnowledgeXXX -> DocumentXXX` 的实现与测试落地

这样可以先把架构方向拉正，而不会把本次需求扩大成一次高风险的大规模重命名。
